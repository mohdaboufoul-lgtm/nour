# Nour — Roadmap: phases 1–3 (SPEC §16, weeks 3–13)

Status: plan. Behaviour authority: `docs/SPEC.md` (§ refs); structure: `docs/DESIGN.md` (D§ refs); adapter facts: `docs/adapters/*.md`; running it: `docs/OPERATIONS.md`. Phase 0 (weeks 1–2) is the DESIGN/MODULES build. This file starts where it ends: every signature named below as a "body" already exists in phase 0 with a refusal or `NotInPhase` path (D§3.13 `VaultStore.expiring/share`, `BeneficiaryService`; D§3.16 `CategoryState`; D§3.18 `handler=None` stubs), every table named as "exists" is in D§5, every port named as "reserved" is in D§3.4 with a record-only fake in `nour/fakes/reserved.py`.

## 0. How a capability lands (the same recipe in every phase)

1. **Config first.** A row in `config/capabilities.yaml` (`id, capability, desk, tier, phase, categories, tools, routine`) and its categories in `permissions.yaml` (`high_impact_actions`, `ask_every_time`, `readback_categories`, `second_channel_required` as the §7 tier demands), `spend_tiers.yaml` (`always_K`, `monthly_cap` holders) and the coat's `approval_rules` (`category_started_at`). `load_config` refuses an unknown category (D§3.6), so this step gates the rest. New categories start at K (`default_new_category`) for two weeks (§6).
2. **Port** (only for a new external system). A `typing.Protocol` + frozen DTOs in `nour/core/ports.py`, every side-effecting method taking `PortCall` first; a field on `PortSet` and a `for_desk` rule saying which desk may hold it; a fake in `nour/fakes/<port>.py` that records into `CallLog`, has an inbound queue and `fail_next`; `default_fakes` wires it. The real adapter is one file `nour/adapters/<system>_<vendor>.py`: sync `httpx`, lazy SDK import, request-shape tests only, never in the gate install (D§2.1, D§9).
3. **Table.** A mapper in `nour/db/models.py` with `__scope__` and `__append_only__`/`__single_transition__`/`__forward_only__` per D§5, plus an alembic revision `nour/db/migrations/versions/000N_phase<N>.py` carrying trigger/RLS DDL from the `nour/db/engine.py` generators. `test_migrations_match_metadata.py`, `test_db_wall.py` and the `postgres` CI job stay green.
4. **Tool.** A `ToolSpec` + handler in `nour/tools/<area>.py`, registered through `register_common` / `register_assistant` / `register_operator` (D§3.18). Every tier-relevant attribute (`default_tier`, `high_impact`, `outbound`, `spends`, `in_owner_name`, `data_tier_max`) lives on the spec, never in model output. Routines go in `nour/tools/routines.py` with a timer name in `Scheduler.tick` and a slot in `calendar.yaml:daily_rhythm`.
5. **Tests.** Unit tests beside the module; one `@pytest.mark.weekly` scenario in `tests/scenarios/` asserting the §18 triple (tier, log entry, owner message) with `Harness.expect`, `verify_chain()` and `replay(day)`; the phase gate in `tests/gate/test_phase<N>_gate.py` (`@gate`); `tests/gate/test_capability_dod.py` extended so every row with `phase <= N` has a tier, a registered `ToolSpec`/routine, a log format and a scenario marker (§16 definition of done).
6. **Dry run, then live.** A new playbook or category runs one week in simulation (`PortCall.dry_run`; `Settings.dry_run` is per desk process, so the Assistant can draft live while the Operator is still simulated) before the first real send (§8).

Wave rule for every new file (D§8): tools/agent import ≤ policy|governance; adapters import `nour.core` only; `nour.vault` is never imported by `nour.tools.common`/`operator`; `lint-imports` and `tests/unit/test_wave_imports.py` fail the build otherwise. Each phase lists its **core edits** (enum members, optional contract fields): those are the only `nour/core` changes allowed, and `tests/unit/test_walls.py` must stay green after them.

### 1.3 Sequencing, owner inputs, risks

- **Order.** Week 3: P1.1 (runtime, adapters, ingress) ∥ P1.2 (tools/mail) ∥ P1.5 (vault, tools) ∥ P1.8 (policy) — four modules in distinct waves, no file overlap. P1.1 lands first; the Assistant goes live on real coat mailboxes by week 3 day 3, which starts the 14-day review window. Week 4: P1.3, P1.4, P1.6, P1.7 and `docs/adapters/telephony.md`. The gate review is end of week 4 if the window started on time, else week 5; phase 2 build starts either way, phase 2 live steps wait for this gate.
- **Owner inputs before start** (§17): OAuth delegation per company mailbox (Graph `Mail.Read + Mail.ReadWrite`; Gmail `gmail.readonly + gmail.compose`, draft-only enforced in the port — mailbox.md §1), calendar scope consent; the knowledge interview and commercial mandate per company; scanned vault documents with tiers and expiries confirmed; hosting region, model vendor and fallback decided; the voice lock approved; SPF/DKIM/DMARC on each coat domain (DMARC `p=none` → `quarantine` during the phase, mailbox.md §5); the WhatsApp line registered with `data_localization_region: AE`; the bake-off winner (chooses the STT adapter); provisional 2027 holiday entries acknowledged (calendar.md §5).
- **Risks.** RLS under the hosting pooler (D§10) — proven by `test_pg_rls_pooler.py` before go-live, transaction pooling required. Gmail cannot express draft-only at scope level, so `scopes()` is the control (`test_mailbox_scopes.py`: `send` raises). Meta retries and batches webhooks (wamid unique index already dedupes). Arabic PDF rendering quality (owner reviews the first render of each template). The two-week window is the whole phase: a slip in P1.1 slips the gate, not the build. LeakGuard is value-based, so Tier 2 prose is protected only by `Tier2Value`/object storage: `vault.share` returns a link, never text (test above). Injection-scanner false positives cost owner time in the window — tune `patterns.yaml` from `found_instruction` rows weekly, never below the five gate vectors.

## 4. What never changes

The eight walls of D§4 are not extension points. A phase may add tools, ports, tables, config rows, timers, enum members and optional contract fields; it may not touch these, and the named tests must stay green on every merge:

- **(a) Desk wall.** `PortSet.for_desk(OperatorToken)` keeps `owner_mail=None`, `private_model=None`, secrets `scoped("operator/")`; `VaultStore` takes an `AssistantToken`; `DeskWallGuard` scopes and the PG roles/RLS from `pg_roles_ddl`; `HandoffQueue.push(AssistantToken)`/`take(OperatorToken)` with `Tier0Ref` facts and no reverse path; import-linter contracts (tools.common/operator never import `nour.vault`; the auditor never imports desks, gate, loop, vault). Every new `PortSet` field states its `for_desk` rule. Tests: `test_db_wall.py`, `test_handoff.py`, `test_operator_isolation.py`, `test_wave_imports.py`, `lint-imports`.
- **(b) Tier 2 never in prompts, memory, logs, index.** `Tier2Value` is not a `str`; `RenderWitness(` only in `nour/vault/renderer.py`; `SafeStr(` only in `nour/core/leakguard.py`; `.decrypt(` only under `nour/vault/`; `CHECK (tier <> 2 OR content_text IS NULL)`; `EncryptedBytes` accepts only `Ciphertext`; Tier 2 hashes are keyed. The private model (P3.8) and vault share (P1.5) return refs, hashes and links. Tests: `test_walls.py`, `test_tier2_value.py`, `test_leakguard.py`, `test_renderer.py`, the `LeakIbanPolicy` gate run.
- **(c) No wrong-tier execution.** `TierResolver` rules only raise (`ActionTier.highest`; new rules append, and `test_tiering::test_monotone` is extended for each); `model_claimed_tier` is never routed on; execution needs a `ReleaseToken` burnt in `releases`; `mint` only in `ActionGate.dispatch` and `ApprovalsQueue.decide`. Tests: `test_tiering.py`, `test_executor.py`, `test_approvals.py`.
- **(d) Authentication server-side.** `Authenticator.stamp` is the only `Event` producer; `IngressRedactor` extracts, verifies and redacts the passphrase before persistence; voice never verifies; first wrong attempt freezes `HIGH_IMPACT`. Staff, sub-agents, screens and pages never gain `owner_verified`. Tests: `tests/gate/test_passphrase.py`, `test_authenticator.py`.
- **(e) Observed content is data.** Everything non-owner is `ObservedText` fenced with `Authority.DATA`/`STAFF_REQUEST`; rule 7 forces K on found instructions, rule 8 means money, vault, beneficiary and owner-name sends can never execute from an observed event.
