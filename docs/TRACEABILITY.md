# Nour — Requirements traceability matrix (SPEC → DESIGN → tests)

Generated 2026-10-02 from `docs/SPEC.md` (§1–§18), `docs/DESIGN.md` (§2–§8, esp. §3 interfaces, §4 structural enforcement, §7 test plan, §8 waves), `docs/MODULES.md` and `docs/build_plan.json`. One table per SPEC section; one row per normative sentence or table row.

Columns
- **ID**: `R-<section>-<item>` (e.g. `R-06-012` = SPEC §6 item 12).
- **Requirement**: brief quote or paraphrase of the normative text.
- **Phase**: delivery phase per SPEC §7 (capability register) and §16 (build plan): `0`, `1`, `2`, `3`; `gov/process` for drills, reviews, checklists and operating practice; `owner input` for §17 items only the owner can supply. `0 sig / N body` = signature and refusal path in phase 0, body in phase N.
- **Module / file**: build module (DESIGN §8) and the file(s) per DESIGN §3.
- **Mechanism**: `type` (a Python type that cannot be misused), `wall` (process/credential/DB/import wall), `cap` (limit enforced outside judgement), `separate store` (own table/namespace/process), `second party` (owner, second channel, auditor, callback), `config` (data in `config/*.yaml`), `process` (human practice, not code).
- **Test**: `file::test` where DESIGN §7 names one, else the owning module's test file. `—` = no test named (a gap when phase is 0).
- **Status**: filled by the build lead; everything starts `planned`.
